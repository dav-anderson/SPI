# spi: design notes

## What it is, and what it is not

A thin layer over `psp-mint`, `esp-mint` and `bitcoind` for the person who runs them, and over the two programs an SPI needs beside them: the stock AIR server and its own ecash-wallet. One config, one command line. It has no mint logic and no keys. It does not hold the mints' state; it writes their config files, starts and stops their processes (a try-out; a machine with services uses the service manager), and reads their public endpoints.

**It drives the binaries; it does not link the mints.** Either way worked, since both mints are libraries and binaries. Driving the binaries needs no change to either mint, no git dependency on them (so spi builds even while a mint's tag is moving), and gives the same behaviour as the service definitions, which also run `psp-mint serve` and `esp-mint serve`. Linking would have meant calling the mints' internals (`Config::load`, the server startup) that are not an interface. The only dependency on the family is `sp-wire`, for `ESP_PER_PSP`, so the unit constant exists in one place.

**Linux is the target; macOS is for development.** spi is designed to run on a Linux system with systemd. The macOS commands and launchd files exist so that spi can be tried and tested on a Mac, and nothing is built to make macOS a production system (its service logs, for one, are not rotated).

**The shared code is air-minterface.** What spi and `aso` both do (list and download releases and check their SHA-256, compare tags, swap a binary in with a rollback, schedule an upgrade, keep logs under a cap, expand a service-file template, write the AIR server's environment) lives in the `air-minterface` crate, which spi uses by git tag. It knows no program: spi gives it two small traits, `Operator` (on `Spi`) and `Managed` (on `Program`), in `src/interface.rs`, and the sentences whose wording is spi's own come from `Managed::say`. The commands, the prompts, the `[bitcoind]` download with its gpg check, the units and the settings stay in spi. That crate's own DESIGN.md says what belongs there.

## One config, generated files

`spi.toml` is the only file an operator edits. `install` and `start` write `generated/psp-mint.toml` and `generated/esp-mint.toml` from it, each starting with a header that says it is generated and will be overwritten, and start each mint with `PSP_CONFIG`/`ESP_CONFIG`, `..._DATA_DIR` and `..._NETWORK` pointing at them. Values spi names (network, the bitcoind connection, the addresses, the PSP URL the ESP mint burns at) are set from the spi config. **Everything else is pass-through**: whatever is under `[psp.settings]` or `[esp.settings]` is merged into the generated file as it is, so a new mint setting needs no change in spi, and spi never validates a mint setting (the mint does, at start, with its own list of problems).

A key spi sets is refused under `settings`, naming the key. The alternative, letting the pass-through win, would let the generated file disagree with what `status` and `audit` assume (the network, the addresses). Both files are rendered before either is written, so one wrong key leaves the old files whole.

Defaults that depend on the network (RPC port, cookie path, wallet name) are computed by spi and **written into the generated file explicitly**, so spi and psp-mint cannot disagree on them. They are the same values as psp-mint's README "Networks" table.

## Regtest by default

The network setting defaults to regtest and is only ever main if the file or `SPI_NETWORK`/`--network` says so. The default ports, cookie and wallet follow the network. `status`, `audit` and `install` compare what bitcoind and the mints report against the configured network and fail on a mismatch (bitcoind's `chain`; the mints' `network` in `/health` and `/audit`).

## Start order, and the sync

`start`: write configs, start bitcoind if it is not answering, wait for it to finish its initial block download, start psp-mint, start esp-mint.

**Why wait, and not start psp-mint and let it report not-ready.** psp-mint scans the wallet through the node, locks the price at the first confirmation it sees and settles at the configured depth. On a node that is behind it would see an old part of the chain: payments arrive late (no harm), but it would also be answering `/health` ok, and the ESP mint and the wallets point at it from the moment it is up. Not starting it means nothing is exposed that is behind. The cost is that on a fresh mainnet node `start` can take days; that is bounded (`bitcoind.sync_wait_secs`, 600 by default), and when it runs out `start` says how far the node is and starts neither mint. bitcoind is left running and `start` is run again. `status` reports the same state ("not ready: bitcoind syncing 63%") for a psp-mint that was started some other way, such as by a service manager, so the two paths agree on what "not ready" means.

**bitcoind is only stopped by spi if spi started it** (a marker file in `run/`). One that was already running is never started over, stopped or restarted. `bitcoind.manage = false` makes spi never start one.

**What "syncing" means.** `initialblockdownload` true and either headers ahead of blocks or `verificationprogress` under 0.9999. The flag alone would keep a fresh regtest node "syncing" until its first block (Core keeps the flag while the tip is more than a day old); on a caught-up chain that is not syncing. Unreachable (no answer, bad cookie) and wrong chain are separate states and never reported as syncing.

Processes are started in their own process group, so Ctrl-C at the terminal that ran `start` does not stop them, with their output appended to `logs/<mint>.log` and the pid in `run/<mint>.pid`. Stopping is SIGTERM, as in the service definitions, and waits for the process to leave. `kill` is the `kill` command, to keep spi free of a libc dependency.

## The AIR server and the SPI's wallet

**One config for the server the mints talk through.** The mints reach wallets only over AIR, so a mint that points at no server, or at a different one from the wallet, is an SPI that does not work. `[air] name` and `[air] host` are therefore set in one place and written into the psp-mint file, the esp-mint file and the wallet's config (`air.server`, `air.host`); a pass-through of those keys is refused like any other named key. `air_server` itself is not changed. It is configured by its environment (`AIR_SECRET_FILE`, `AIR_STORAGE`, `AIR_WS_ADDR`, `AIR_HEALTH_ADDR`, and `AIR_TLS_*` when it has a certificate), which spi generates from `[air]` (`generate::air_env`): into the unit's env file on a service, into the process on `spi start`. nginx in front of it is optional and only a generated file (`nginx-air-server.conf`) that spi does not install, since nginx's folders differ by system.

**The identity is the operator's.** The server's identity file is its name; losing it changes the name and every mint and wallet then needs the new one. spi does not make it (how an operator makes it or learns the server's public name from it is not something this version verified: `[air] name` is written by hand), does not back it up, and says so when it writes the service. `start` refuses to run without `[air] name` and without the identity file, and `install` warns about the missing name, because psp-mint refuses to start without `air.server`.

**Fees.** Stock air_server 1.0.1 has no fee hook. `fee_read` and `fee_write` exist so that the setting has one named place, and any value but 0 is refused, naming upstream item 1 (the air_server fee hook), instead of being accepted and not charged.

**Start order** is bitcoind, the AIR server, psp-mint, esp-mint (`spi start`; `After=` in the units). Health is a line of `status` (the server's health address answers a bare `ok`), so a mint that is up with no AIR server shows why no wallet reaches it.

**The wallet is spi's, in the sense that spi writes its config.** `generated/ecash-wallet.toml` is built from `[air]` and the mints' DIDs (read from `<data>/<network>/mint_did_key.json`, which both mints write; spi asks `pubkey` only when the file exists because `pubkey` would make it), plus `[wallet.settings]` as given. `config show` prints each wallet setting with the source. The wallet is run by the operator, as themselves, with the printed command line; spi runs it only to read the balance and to take in notes.

**Setup is steps, and "ready" is step e.** a bitcoind, b AIR, c PSP, d ESP, e PSP in the SPI wallet (required), f FSP bought elsewhere (recommended, never tracked: spi can not know what backups the SPI wants). The wallet is not asked until a to d are done, because it needs the AIR server and the PSP to answer, and an SPI whose wallet holds no PSP can not do what an SPI is for, so it is not ready. There is no "open channels" step: nothing in this design opens channels. The genesis SPI has no PSP to buy PSP with, so it buys from its own PSP mint with every fee off (a fee it paid itself would only shrink what it buys); the other way in is a hand-off from another SPI.

## What the PSP the SPI is paid becomes

Earlier, every PSP paid to the SPI (the `pay` of a spend) was burned. **That is superseded**: the SPI needs PSP to buy services, so by default psp-mint reissues `pay` as notes for the SPI's wallet, one file for each request in `revenue/` under the network's data folder (the file format is `sp-wire`'s `PspHandover`), and `spi collect` takes them in with `ecash-wallet receive-psp`. The notes are signed by the mint itself and are then swapped by the wallet for notes only it knows, so a stolen file is worth nothing after that and is cash until then. Burning is opt-in (`[psp] burn`, `burn_threshold_psp`): with it on, psp-mint reissues paid PSP only while the SPI's wallet holds less than the threshold, and burns the rest, counted as revenue. **The figure compared is the SPI wallet's current PSP balance**, not a running total over the mint's life (decided by the PM). psp-mint cannot see the wallet, so `spi` publishes it: `spi collect` (after it has taken the reissued files in) and `spi audit` write `{"psp": W, "reissued": R, "at": T}` to `[psp] burn_balance_file` (psp-mint's `burn.balance_file`; by default `wallet_balance.json` in psp-mint's network folder, and `<service data_dir>/spi-share/wallet_balance.json` for a service, a folder `install-system.sh` makes group-writable and setgid so `spi`, run by a member of the service group, can write it and the service user can read it). `W` is `ecash-wallet balance`, `R` is psp-mint's `reissued` total from `/audit`, read **after** `W`, and `T` is when `W` was read; the file is written to a temporary name and renamed, mode 0640. At each spend psp-mint takes `held = W + (its reissued now - R)`, so PSP it reissued since the reading counts as held even though the wallet has not taken it in yet, keeps `min(pay, threshold - held)` for the wallet and burns the rest. When the wallet spends and `spi` publishes a lower balance, reissuing starts again; burning turns itself off. Reading the wallet first makes the one race (a note reissued between the two readings) fall towards keeping, never towards burning. **No usable figure means no burning**: if the file is missing, malformed, older than psp-mint's `burn.balance_max_age_secs` (24 hours by default) or dated ahead of its clock, psp-mint reissues the whole of `pay`, and logs why once. So a `spi` that is not run costs the burning and never the revenue, and `spi collect` and `spi audit` say when they could not publish (`collect` fails, `audit` warns). The figure is refreshed by `collect` and `audit` only, and by `spi publish-balance` by hand: no timer, because each publish runs `ecash-wallet balance`, which talks to the AIR server and the PSP, and the figure only has to be close (decided by the PM). spi has no command that spends from the SPI's wallet; **a spend made with ecash-wallet directly is not seen by psp-mint until the next `collect` or `audit`**: until then psp-mint thinks the wallet holds more than it does, so it keeps less for it and burns more than the threshold asks.

`collect` keeps `received.txt` (the names of the files taken in) so that a file is not offered twice; a file the wallet says it has already is recorded and is not an error, so a crash between the wallet taking a file and spi writing the name costs nothing.

## Uptime

Nothing stops a mint except an upgrade, a setting that needs a restart, and `spi stop` (a try-out, and decommission). **Both of the first two are a brief downtime**: the old process stops, then the new one starts. This is decided (2026-10-23): upgrades with no downtime are deferred, and the analysis for them is kept apart from this file (ROADMAP item 25 and its draft). A settings change that "reloads live" is a SIGHUP and stops nothing; `status`, `audit` (including the wallet), `setup`, `collect`, `versions`, `upgrade check`, `snapshot` and `publish-balance` only read or signal. A restart after a crash is fault recovery (`Restart=on-failure`, `HEALTH_ACTION=restart`) and stays.

**Why a mint's restart is a stop and then a start.** One process holds a mint's data: sled takes an exclusive lock on the folder, so a second process cannot open it while the first holds it, and the new build can only start after the old one has stopped. While the mint is down a wallet's request waits in its mailbox slot on the AIR server, which stores a created record with no expiry, and is answered when the mint is back. Every mint line `spi upgrade`, `spi restart` and `spi reload` print says this in the same words (`upgrade::MINT_DOWNTIME`).

**Settings: live or restart.** Each mint marks every setting in its code (`SPECS`, a `reload` flag) and README: *reloads live* (read again on SIGHUP and applied to the next request or scan) or *needs a restart* (built into something the process holds for its life: the listening sockets, the chain and the wallet, the key schedule, the AIR connection). A reload that changes a restart-only setting leaves the running value alone and says so; `spi reload` names each such setting with the old and the new value, and `spi restart` applies them. spi keeps its own copy of the restart-only keys (`run::RESTART_ONLY_PSP` and `_ESP`) because it does not link the mints; the two must be kept in step by hand.

**`spi upgrade` asks first.** It prints one warning (the AIR service and every mint it runs are shut down, one at a time, each for a brief downtime), the plan, and asks for a `yes`. With no terminal it asks no one and changes nothing. A dry run asks nothing and changes nothing. The question is the same when the upgrade is scheduled (`--at`, `--in`) and is asked when it is scheduled; the scheduled run asks nothing. The scheduler is a systemd timer (written in UTC, `Persistent=true`, `OnBootSec` for a machine that was off) or a launchd job; a run more than an hour late is skipped and logged, and either way the job removes itself. One upgrade is pending at a time.

**What an upgrade installs.** `version` in spi.toml is an optional pin. With none, the target is the newest tagged release; with one, exactly the pin. A pin that is behind the newest release is warned about wherever it matters (`upgrade`, `upgrade check`, `upgrade status`) and asked about at each `upgrade`; `--keep-pins` and `--reset-pins` answer for all. A reset edits spi.toml with a backup and keeps everything else in it, comments included. spi only downloads release binaries (checked against a SHA-256) and never builds; air_server publishes none, so its `bin` and `version` are the operator's. The release source is `fetch::CurlSource` (`main` builds it): `curl` run through the same `Exec` as every other program, so no HTTP crate is added. Downloads go to `<spi dir>/releases/<program>/<version>/` and are pruned to `[release] keep` after a good upgrade, never removing the installed version or the one it replaced. A bitcoind written as `bin` is the operator's override and is never downloaded; with `manage = false` spi leaves bitcoind alone. For bitcoind the `SHA256SUMS` is itself checked first, with gpg (`src/signature.rs`): its `SHA256SUMS.asc` is verified in a private keyring (`<spi dir>/gnupg`) loaded with the builders' keys, and the download goes on only when at least `[bitcoind] min_signatures` (7) of the compiled-in builders, each counted once by the primary fingerprint, signed and no signature is bad; only then is the archive's line in `SHA256SUMS` trusted. There is no opt-out, and without gpg spi refuses to download bitcoind. A release candidate is never the newest and never installed, even when pinned (config load refuses the pin).

**After the restart, the version is checked.** A mint that is healthy on the old version did not take the upgrade: `/health` must report the version installed (`versions::same_version`) before spi says "now x, healthy"; otherwise the old binary is put back and the run stops.

**bitcoind: no outage for the mints.** It restarts; psp-mint reads the chain through it and picks up from its checkpoint. psp-mint's `/health` and the mints' AIR listeners keep running.

**air_server 1.0.1: a brief downtime, read in the checkout efef621.** It cannot be replaced without a stop. It has exactly one SQLite writer (`deploy/README.md`, "Durability and capacity"); a wake-up reaches only readers attached to the same process (`server.rs:385-395`); `Server::start` (`server.rs:83-122`) has no way out except a `panic!` in the `select!` at `:115-121`, with no drain mode and no clean close of the storage worker; and its listeners are bound by the process itself (`websocket.rs:169-171`, `server.rs:127-128`), with no inherited descriptor. What the restart costs is small and safe: a created record is stored with no expiry (`server.rs:872-888`), the reply cell is write-once, a pending read is held per session (`:588-610`) and completed by a later create (`:616-651`), with limits of 256 pending reads per session (`:597`) and 512 response slots (`:792`), and `deploy/README.md` says pending reads and the response state persist across server restarts. So a wallet's request waits in its mailbox slot while air_server restarts and is answered after; what the wallet sees is a reconnect. A client *process* restart loses its resume token (it is kept in memory), which is the client's, not the server's.

## Backups, restore and configs

**Item 15, a backup with no stop: built, as a drop-and-reopen snapshot.** On SIGUSR1 a mint stops its threads, checks that its stores are released, copies its network data folder to `<data folder>/snapshots/<UTC stamp>/` (mode 0700, every file fsynced, the `snapshots` folder itself skipped), writes `snapshots/LATEST` last by rename, and opens its stores again. A failed copy is removed and the mint goes on. Copying a sled folder while it is open is not safe, so the stores are dropped first; that is the only deviation from "take the locks and wait", and it is what guarantees nothing is mid-write. **The pause** is the copy and fsync of the whole folder plus sled's open time, so it grows linearly with the size of the database; during it, connections wait in the listener's backlog and requests wait in air_server's slots, as in a restart. **The snapshot holds the keys** (it is a copy of the folder), so treat it like the folder. A test restores a snapshot taken while the mint serves into a second mint and checks that its `/audit` matches. `spi snapshot` sends SIGUSR1 to both mints through the service manager (each mint's README has the commands). If a task still holds a store when the snapshot starts, the mint refuses the snapshot, logs it and exits 1, and the service manager restarts it: that is a restart, and it is the one case where a snapshot stops a mint.

**Item 9, configs in backups, restore and merge (the PM asked for these to be stated precisely).**

- **DID keys are never in an AIR backup.** The operator backs them up offline. The AIR server's identity file likewise.
- **Signing keys are in the AIR backup.** `mint_keys.json` and `master_secret.hex` are backed up to the AIR, sealed to the DID key, so a restore needs the DID key and nothing else the backup holds.
- **ASK: `<mint>.secret.env`.** It holds `ESP_ADMIN_TOKEN` and any other secret the operator put there. Proposal: it is not in the AIR backup and not in an `spi` backup. It is a bearer secret for the operator interface, it carries no history, and it can be set again. A restore leaves it absent, `install` writes an empty one (it already does, and never overwrites), and the operator puts the token back. Whether the PM wants it sealed to the DID key as well is the question.
- **A backup of `spi.toml` and the generated mint and wallet files** is proposed, not built: those files hold no secrets, since secrets are in `<mint>.secret.env`. A restore puts `spi.toml` back and runs `install` to generate the rest.
- **Merge is restore plus merge with the local state that survived (ROADMAP 3f(g)); proposed, not built.** The rule to propose: a spent mark is only ever added, never dropped, so the union of the backup's spent marks and the survivor's is safe; anything else that differs between them (counters, totals) is reported and stops the merge rather than being chosen by the program. Merging two different SPIs' data is not proposed: it would mix two mints' histories.

**Item 7, how long payment records are kept.** Needs psp-mint item 17 first. Proposal: `[psp] payment_record_retention_days` in `spi.toml`, 0 (keep) by default, written to psp-mint as the setting that item 17 defines; psp-mint prunes settled payment records older than that, and reports in `/audit` how many it pruned. Not built here.

## Versions and upgrades

`spi versions` asks each program for `--version` and reads the libraries each was built with from the `Cargo.lock` it was built against (`build.rs` embeds the pins; a build without `--locked` can differ). `air_server` prints none, so spi records the file it installed (a hash, `air/installed.json`) with the version the operator declared and reports that version only while the file still has the hash; a replaced file is "unknown", saying why. Every line is a version or "unknown" with the reason; nothing is guessed.

## Service files

`install` is the whole bootstrap of a machine that runs the mints as services. The operator-facing steps are in the README ("Running as services"); this is why it is built the way it is.

**Embedded templates, generated per `spi.toml`.** An earlier version copied the definitions out of an internal folder of the family, which a fresh machine does not have and which is not published. The definitions are now in `ops/` in this repository and compiled in with `include_str!`, so the binary alone is enough. They are templates, not copies: `{{name}}` stands where a value from `spi.toml` goes (binary folder, user, data, log and settings folders, bitcoind's datadir and arguments, the addresses, the chain). One change in `[service]` therefore reaches every file that mentions it, and there is no fixed `/usr/local/bin` or `spmint` left in the text. The expander is about 30 lines: a placeholder it does not know, or one that is not closed, is an error that names it, so a typo can not end up in a unit as literal text; in a property list the values are XML-escaped.

**`--ops` is an override and never required.** A file in the folder under the name `install` writes (`systemd/psp-mint.service`, `launchd/org.servicepoints.psp-mint.plist`, `sp-health-monitor.sh`, ...) replaces the embedded one and goes through the same expansion; a file that is not there falls back to the embedded one. The old definitions, which had no placeholders, still work this way unchanged. A folder that does not exist is an error and not a silent fall-back to the embedded text.

**Values are restricted instead of escaped.** A path, an account name or a bitcoind argument that goes into a unit may hold only letters, digits and `/ . _ + @ : = , -`. A space or a quote would need a different escape in systemd (which also gives `%` and `$` a meaning), in launchd's XML and in sh, and a unit with a wrongly escaped path is a service that does not start, or starts something else. Refusing the value, naming the setting, is simpler than being sure of three escapers. `bitcoind.datadir` on a Mac in `~/Library/Application Support` is the case that hurts, and it is only checked when spi puts it in a service (a `spi start` is not affected).

**A script and printed steps, not a `--system` flag.** `install` could have done the root work itself behind `--system` (create the account, copy the files, load the services). It does not, for these reasons:

- spi stays an ordinary user's tool. Running as root, or calling `sudo` from inside a program, makes the program's every bug a root bug, and `spi start`, `status` and `audit` should never be run that way; an install that needs root in the middle of a command that otherwise does not is easy to run wrongly.
- Creating accounts, writing under `/etc` and loading services are changes that should be read before they are made. A plain sh script of `install` and `dscl`/`useradd` lines can be read, kept, copied to another machine (it takes its files from its own folder) and run again, which an in-process step can not.
- It is testable. The tests build the folder and check every file and every line of the script, for both systems, without a system to damage. A `--system` flag could only be tested by running it, as root.
- No password or secret passes through spi. The admin token is never in `spi.toml` or in a generated file; the script installs an empty file for it that it never overwrites.

The cost is one more command, `sudo sh ~/.spi/service/install-system.sh`. A `--system` that runs exactly that script could be added later without changing the files; it is not here because it adds the first place spi runs as root.

**Idempotent, and what it keeps.** Running the script again replaces what spi generates (settings, env files, definitions, the monitor script, the binaries) and keeps what a person edits: `<mint>.secret.env` and `<mint>-health.conf` are installed only when they are absent. Env files could not hold the admin token if they were overwritten, and the monitor's tunables would be lost on every settings change. What the monitor watches (its URL, its name, its restart command) is not in the kept file: the definition sets it with `Environment=` (systemd) or `EnvironmentVariables` (launchd) from `spi.toml`, and the monitor already lets the environment win over its file, so an address that changes in `spi.toml` is not stale in a file that nobody regenerates.

**Paths and the service user.** The units run the binaries from `bin_dir`, to which the script copies them from where spi found them (`PATH`, or the path in `spi.toml`), because a service user can not read `~/.cargo/bin` and `ProtectHome` hides it. A binary spi can not find is a warning and a guard in the script (it warns when the file is missing), not a failure: the folder is useful on a machine that gets its binaries another way. `StateDirectory` is not used, as it only means `/var/lib`; the units name their data and log folders with `ReadWritePaths`, so `data_dir` can be anywhere, and the script makes the folders.

**One account for all services.** psp-mint has to read bitcoind's RPC cookie. With bitcoind under the same account, as the service writes it, the cookie needs no change of permissions and no copy. The cost is that a compromise of one service has the others' files; separating them would mean a group for the cookie and a second set of files, and was not worth the added moving parts here. The mints' own data is 0750 and their processes run with a 0077 umask.

**The service bitcoind, and its cookie.** When `bitcoind.manage` is true the script installs a unit for bitcoind: in the foreground (no `-daemon`, which would make `Type=simple` lose it), `-datadir=` from `bitcoind.datadir` or `<data_dir>/bitcoind`, the chain flag, `-rpcport=` only when the URL's port is not the chain's own, `bitcoind.args`, and `-rpccookieperms=group`, and `-nodebuglogfile -printtoconsole`, so that the whole log goes to the unit's stdout (`bitcoind.log`, which spi's log rotation covers) instead of a `debug.log` that Bitcoin Core trims only at start. `spi start` does the same: it runs bitcoind in the foreground (a child of its own process group; no `-daemon`, which discards the console) with the console appended to `logs/bitcoind.log`, rotated like the mints' logs. It is `sp-bitcoind.service` and not `bitcoind.service` so that it can not replace a unit that a package installed. psp-mint's service settings point at the cookie that this bitcoind writes (`<datadir>/<chain folder>/.cookie`) unless `bitcoind.cookie` was written down, in which case that path is used and a warning says so if it differs. The group-readable cookie is for the operator: `spi install` and `spi status` run as a person need to read it, and the alternative (running spi as root, or as the service user) puts spi in the root path the previous section avoids. It does give whoever is in the group the node's RPC password, and the README says so. With `manage = false`, spi writes no bitcoind unit and the cookie is whatever the config says; a cookie in a home folder gets a warning and `ProtectHome=read-only` on the psp-mint unit, since the default `yes` would hide it.

**An absent bitcoind is not a failure of the install that starts it.** On a fresh machine bitcoind is not running when `spi install` first runs, and failing there would make the bootstrap exit non-zero when it has worked. When service files are being written and spi manages bitcoind, an unreachable node is reported as "not running yet", and the step that sets up the wallet is left to a second `spi install --no-service-files` once it answers (printed in the steps). A node on the wrong chain still fails, and `--no-service-files` and `manage = false` keep the old rule, because nothing then starts the node.

**The services do not wait for the sync.** `spi start` holds psp-mint back until bitcoind has synced (see "Start order, and the sync"). A service manager can not do that with its ordering alone: `After=` waits for bitcoind to be started, not for its RPC, let alone its sync, and launchd has no ordering. The units therefore order the mints after bitcoind where they can, and rely on psp-mint's own behaviour and the restart policy for the rest, and `status` says "not ready" while the node syncs. This is the one place the service path is weaker than `start`, and the README says so. A unit that waited (`ExecStartPre` polling `getblockchaininfo`) would need `curl` or a helper in the unit and the cookie in it; not done.

**Logs are kept under a cap by spi, not by logrotate.** An earlier version wrote a logrotate file. The services are meant never to stop and the logs a unit writes are held open by it, so one mechanism had to do two jobs: at a service's start (`ExecStartPre=-spi logs rotate`, so a failed rotation never stops the start, and with `StandardOutput=append:` the file is opened again for each start) a log over `log_max_size_mb` is moved aside, and while the service runs a timer (`sp-logs.timer`, 5 minutes) copies a log over the cap aside and empties it in place (`--running`), because a rename would leave the process writing to the moved file. The copy-and-empty step assumes the writer opened the file for appending, so its next write goes to the new end; that holds for `append:`, and it is the thing to check first on a real machine. The timer runs as root because the health monitors and the scheduled upgrade write their logs as root. A log can pass the cap by what is written in 5 minutes, and `.bak` copies are owner-only. macOS is not rotated (it is a development machine).

**What is not tested.** The tests check the files and the script text and `sh -n` the script; none runs the script, systemd or launchd. See the README, "Tests".

## The audit

`audit` is `psp-mint GET /audit` and `esp-mint GET /audit`, combined.

- PSP outstanding is psp-mint's `outstanding` (whole PSP).
- ESP is esp-mint's `outstanding` (ESP units), shown as matured and unmatured when esp-mint reports them (0.5.0 and later). Both are at full value. Nothing is discounted for waiting. The two must add up to `outstanding`, or the reply is refused, unless esp-mint says it has unfinished requests, which it has not counted yet (then a warning says so).
- FSP is left out. It is issued 1:1 against ESP that the FSP mint then holds, and that ESP is in esp-mint's outstanding; counting FSP too would count it twice.
- Every line is in its own unit, in PSP (`units / ESP_PER_PSP`, or the PSP count) and in USD (PSP / `PSP_PER_USD`, 10). They are exact decimals from `u128` integers. Each addition and the PSP to ESP scaling is checked, and an overflow is an error. The largest PSP count that fits is about 3.4 x 10^27, far beyond any real figure but not infinite.
- `PSP_PER_USD` is the one place the rate is held, with a comment that it must match the payout rate. The economics (what a payout costs, fees on payout, any surplus) are not here or in any repo.
- A network mismatch in an `/audit` reply, a non-200, or a mint that does not answer is an error: a report from a mint on another network or no report at all is never shown as zero.

### The esp-mint split (made in esp-mint 0.5.0)

esp-mint's `GET /audit` used to count issued and redeemed from mint-core's totals, which do not know the redeemable-after day. Matured and unmatured outstanding ESP needs a figure by terms (service and day), and it could not be derived from what esp-mint stored: an exchange, a transfer and a decline were stored in the same `done` shape, and a redemption's per-terms record covered only what left.

esp-mint 0.5.0 keeps a ledger by redeemable-after day (issued and redeemed), changed in the same atomic write that finishes each request, and `/audit` adds `outstanding_matured`, `outstanding_unmatured`, `requests_unfinished` and `as_of_day` (esp-mint's DESIGN.md, "The audit split", has the rules and the crash safety). spi reads them as they are; the day rule is esp-mint's (`Terms::is_redeemable_at`), not spi's, so spi does no date arithmetic.

What spi does with them:

- **The parts must add up.** matured + unmatured has to equal `outstanding`. A reply where it does not is an error, because a report whose lines do not add up to its total is wrong somewhere and should not be read as right.
- **The one excuse is an unfinished request.** esp-mint's counters move as each note is burned or signed, and its ledger when a request finishes, so for a moment the two differ. esp-mint says how many requests are unfinished. If any are, spi accepts the gap and warns; the total is still esp-mint's `outstanding`.
- **An older esp-mint** gives none of this: ESP is one figure and a warning says the split needs 0.5.0.

## Not done

- The real mints are not started in the tests (see the README).
- The health monitor is a shell script (the same one the mints have always used, embedded unchanged); spi has no monitor of its own.
- The service script has not been run on a real Linux or macOS machine by the tests; run a first install on a test machine.
- `start` and `stop` manage processes of the current user. They do not talk to launchd or systemd. `spi upgrade` works on the service install only. It restarts each program, one at a time, after a warning and a confirmation (see "Uptime").
- Payment-record retention (item 7) is not built, by decision; backups of configs, restore and merge are proposals above. The AIR server's identity is not made or backed up by spi. The restart-based upgrade, the scheduler, the pins and the snapshot are written but have not been compiled or run by the author (see the report); the release source is not built.
- Nothing here has been compiled or run in the environment this was written in (no registry access): see the report.
- spi never manages fsp-mint, and writes no service files for it. spi is psp-mint, esp-mint, bitcoind, the AIR server and the SPI's wallet only. An FSP mint is run through the operator control interface of the AIR service it belongs to, and has its own `audit` (the figure here leaves FSP out).
